# Fondealo: business approval, Passport and agentic verification market

**Status:** Stage 1 code merged via [PR #13](https://github.com/adletgamer/Fondeal0/pull/13), 2026-10-11. CI passed. Production migration and deployment status must be verified separately; this work did not perform either. No contract was deployed as part of the PR.

## 1. Verified baseline before Stage 1

- `apps/web/src/lib/actions/kyb.ts` accepts a business when `sandboxDecision(taxId)` accepts it. The same transaction writes `KybSubmission(Accepted)` and `PassportProjection` with score 500. There is no separate underwriting decision or evidence review.
- The KYB wizard confirms documents can be provided; it does not upload or verify them. A sandbox acceptance must never be represented as a real KYB or lending approval.
- `createOpportunity` in `apps/web/src/lib/actions/opportunities.ts` does require a Business session, an accepted KYB submission and a Passport projection. These checks are real, but their inputs currently come from the sandbox path.
- `getKybState` returns `null` on database failure. The business dashboard, new-opportunity and Passport pages redirect only when KYB is non-null and not accepted. `getBorrowerPassport` falls back to a demo Passport. This can display a Passport or business UI when verification is absent or unreadable; the mutation guard is narrower and currently prevents unverified opportunity creation.
- `packages/soroban/contracts/business_passport` already implements a nontransferable credential: owner fixed at issuance, no transfer/approval methods, issuer authorization, freeze/revoke, credentials and persistent storage. The app does not issue it on-chain yet. `loan_escrow` reads a risk band without checking `is_active`. `is_active` checks Passport status, not KYB status. Contract `init` does not require the proposed admin's authorization, so deployment must initialize atomically and contract changes should add an explicit auth check before deployment. *(Update 2026-10-23: resolved by [ADR-0012](../adr/0012-contract-initialization-roles-and-funds-safety.md) — constructors replace `init`, and `loan_escrow` now checks Passport status and KYB.)*
- The contract dependency is `soroban-sdk = "27"` and the installed CLI is 27.1.0. Stellar's [software versions](https://developers.stellar.org/docs/networks/software-versions) list Protocol 29 on Mainnet and Testnet, with SDK 28.0.0 and CLI 28.1.0 recommended. Current SDK 27 contracts pass local Rust tests and WASM compilation; network compatibility remains untested. Do not upgrade dependencies without a separately reviewed compatibility change.

### Stage 1 code merged to main; rollout unverified

New sandbox applications stay `Processing` and create no Passport. A salted, domain-separated KYB commitment replaces the predictable unsalted hash for new submissions. The schema adds versioned, evidence-linked underwriting decisions and an additive migration; its target-environment application status must be checked. Business pages, new opportunity creation and new investor funding fail closed without real KYB, current underwriting approval and a matching Passport projection. Repayment of existing obligations remains available. The client-first Testnet funding attempt is temporarily disabled because it could transfer tokens before the server checked eligibility. Deploying this application code before its new table exists would break database reads. Existing `Open` opportunities from sandbox businesses remain visible, but new funding is blocked until their trust status is reviewed; repayments remain available. Before rollout, identify any partially funded `Open` opportunity and agree on a ledger-reconciled cancellation/refund path so investor balances are not stranded. The code is already merged into `main`; do not deploy it to Production until these gates are satisfied.

## 2. Product meaning and state machine

### First operating jurisdiction: Peru

The first **real** KYB adapter and underwriting policy should cover Peru. Obtain consent and verify a business's RUC and current taxpayer status through an authorized source, then review representative authority and ownership evidence before making an identity decision. [SUNAT's electronic RUC record](https://www.gob.pe/institucion/sunat/pages/7475-obtener-ficha-ruc-electronica) is a candidate evidence source; this project has no verified production API access to it. Determine with Peruvian counsel which obligations apply to Fondealo's actual activity under [SBS AML/CFT rules](https://www.sbs.gob.pe/prevencion-de-lavado-activos/Sistema-de-Prevencion-de-LA-FT) and the [SBS list of obliged entities](https://www.sbs.gob.pe/prevencion-de-lavado-activos/Sujetos-Obligados/Relacion-de-Sujetos-Obligados). Other countries remain sandbox-only until their evidence sources, policy and legal scope have been reviewed.

The Passport is a portable **business identity and verified-history credential**. It is not a promise that every future financing request will be approved. The initial underwriting gate requested here determines whether a new business can enter the financing marketplace; each opportunity still receives a current, amount-specific decision.

`Draft → Submitted → IdentityReview → NeedsInformation | IdentityRejected | IdentityVerified → RiskReview → RiskRejected | RiskApproved → IssuancePending → PassportActive`

Suspension and renewal: `PassportActive → ReviewDue | Suspended | Revoked`; `ReviewDue` or `Suspended` blocks new opportunities until a fresh decision. Retain an append-only history of attempts and decisions rather than overwriting them. Existing accepted sandbox records require explicit classification and review; no bulk promotion to `RiskApproved`.

### Required gates

1. **Registration:** Privy session verified on the server; Business role write-once; wallet tied to one business. Collect country, legal identity, tax ID, authorized representative and consent. Use country-specific fields and a narrow collection policy.
2. **Proportionate KYB:** verify entity existence and registration, representative authority, beneficial ownership as required by the market/provider, sanctions/PEP screening where applicable, and source/evidence freshness. Use `NeedsInformation` and manual review for ambiguous results. The sandbox can remain only in a clearly isolated demo environment.
3. **Initial underwriting:** an explainable, versioned policy consumes *verified* signals such as operating history, cash-flow evidence, requested exposure, fraud flags and existing obligations. Output `Approve`, `ManualReview` or `Decline`, with reason codes, evidence references, reviewer, timestamps, expiry and the policy version. A missing/failed provider response becomes `ManualReview`, never approval. Do not use the Passport's starting score of 500 as evidence of creditworthiness.
4. **Issuance:** a single idempotent issuance intent is created only after both KYB and initial underwriting pass. An authorized worker issues the Passport on Testnet, indexes the `issued` event, reconciles the contract record and then marks the projection active. A failed chain write stays `IssuancePending`; it must not silently become active.
5. **Financing:** `createOpportunity` must read fresh business eligibility and the current approved risk limits inside its transaction. The chain escrow must reject inactive/invalid KYB Passports and enforce risk decisions appropriate to the requested amount. Investor funding and repayments retain current ledger invariants.

## 3. Data and security boundaries

Proposed records (names illustrative): `BusinessApplication`, `VerificationCase`, `EvidenceReference`, `UnderwritingDecision`, `PolicyVersion`, `IssuanceIntent` and `DecisionAuditEvent`. Link every record to a business and verified actor. Use constrained enums, unique idempotency keys, optimistic or transactional state transitions and explicit reviewer permissions. Preserve the existing Business, KYB, Passport and ledger data through additive migrations only after review.

Store documents and personal data encrypted off-chain, with restricted access, retention/deletion rules and vendor agreements. On-chain publish only minimum status, issuer and a commitment. The current SHA-256 commitment over a predictable name/tax-ID bundle needs a fresh, secret random salt and canonicalization before any chain publication; otherwise low-entropy fields can be guessed offline. Keep the salt and evidence off-chain. Do not make an owner-editable `metadata_uri` authoritative for KYB or credit claims.

Apply the same fail-closed eligibility check to protected page reads and all server mutations. Never use `source: demo` as a verified Passport. Enforce role/ownership, KYB recency, active Passport status, underwriting expiry, exposure caps and duplicate-submission prevention on the server. Separate keys for issuer, verifier, reviewer and payment agent; use least privilege, rotation, multisig for privileged contract operations and an incident freeze path.

## 4. Stellar standards and Passport choice

- [SEP-9](https://github.com/stellar/stellar-protocol/blob/master/ecosystem/sep-0009.md) defines interoperable KYC/AML fields; [SEP-12](https://github.com/stellar/stellar-protocol/blob/master/ecosystem/sep-0012.md) defines KYC data exchange and statuses with SEP-10 or SEP-45 authentication. A Fondealo intake may use those field conventions without claiming to be a SEP-12 server or claiming the uploaded fields are verified.
- [SEP-50](https://github.com/stellar/stellar-protocol/blob/master/ecosystem/sep-0050.md) is a **draft** NFT interface that includes transfer and approval. A soulbound Passport should remain a dedicated nontransferable Soroban credential, as already chosen by [ADR-0009](../adr/0009-non-transferable-business-passport.md). It is not SEP-50 compliant and may not appear as a standard NFT in wallets. Add read-only discovery/metadata compatibility only if there is a proven consumer need; never expose a usable transfer path.
- `Address.require_auth` and host replay protection are documented in [Stellar authorization](https://developers.stellar.org/docs/learn/fundamentals/contract-development/authorization). Persistent Passport entries need explicit TTL/restore operations; see [storage guidance](https://developers.stellar.org/docs/build/guides/storage/choosing-the-right-storage).
- Contract events need a durable indexer: Stellar RPC `getEvents` retains at most seven days according to the [event ingestion guide](https://developers.stellar.org/docs/build/guides/events/ingest). Reconcile event cursor, transaction hash, ledger, network and final contract state.

## 5. First agentic market: paid underwriting verification

Pilot on **Stellar Testnet**. The buyer is Fondealo's bounded verification agent. Sellers are approved independent data/verification providers. Example product: an entity-registration check or account-ownership attestation for one application. A listing declares evidence type, country coverage, price, freshness, SLA and schema. The agent requests only the minimum data with consent, pays for one response, validates provider identity/signature/schema/freshness, and stores the receipt and evidence reference. Payment buys a response; it never auto-approves an application. Conflicting or low-confidence evidence routes to human review.

Use one paid HTTP endpoint as a vertical slice. [Stellar x402](https://developers.stellar.org/docs/build/agentic-payments/x402) uses HTTP 402, Soroban authorization entries and a facilitator; the [official quickstart](https://developers.stellar.org/docs/build/agentic-payments/x402/quickstart-guide) is suitable for a Testnet proof of concept. [MPP Charge](https://developers.stellar.org/docs/build/agentic-payments/mpp) offers one-time on-chain payments without a facilitator. MPP channels add prefunding, cumulative commitments and settlement complexity, so reserve them for proven high-frequency demand. Evaluate provider and wallet support, transaction fees and facilitator trust before selecting x402 or MPP for production.

Guardrails: allowlisted service/provider/asset/network; price ceiling per call; budget per application and day; no raw wallet key in model context; short-lived scoped signing authority; human approval for larger spend; idempotent request and payment receipt; replay controls; verified settlement before releasing results; timeouts and dispute/refund policy. The [Stellar contract-account patterns](https://developers.stellar.org/docs/build/guides/contract-accounts/advanced-patterns) cover spend limits, allowlists and session keys. The [MPP Charge guide](https://developers.stellar.org/docs/build/agentic-payments/mpp/charge-guide) explicitly requires a replay store in its current example. Never use production funds in the pilot.

## 6. Delivery sequence and acceptance

1. **Now: containment and design:** correct presentation gates so no KYB/DB error cannot render a verified Passport; mark sandbox as sandbox; define policy and jurisdiction/provider requirements. Tests: unauthenticated, wrong role, no KYB, rejected KYB, DB outage, stale decision and demo fallback all fail closed for financing.
2. **Application flow:** additive data model and audit trail; provider adapter; manual review UI; versioned deterministic underwriting policy. Tests cover duplicate submission, tampering, adverse/review reasons, expiry and reviewer authorization. No production migration until the migration and rollback are approved.
3. **A2/Testnet Passport:** complete the already ordered A1/A2 build gates, then contract auth/lifecycle review, Testnet compilation/deploy/issue/indexer. Tests prove no transfer, unauthorized issue/freeze/score change fails, revoked KYB blocks new financing, TTL restoration, duplicate issuance and event replay reconciliation. No production deployment.
4. **Agentic Testnet pilot:** one provider, one endpoint, synthetic data, bounded USDC Testnet budget. Tests prove wrong asset/network/recipient/amount, replay, unpaid request, duplicate payment, provider failure, untrusted evidence and overspend are rejected.
5. **Production readiness review:** security and economic threat model, independent contract review, vendor/privacy review, measurable decision quality, incident runbooks, reconciliation and rollback. Only then consider live money or wider marketplace.

Likely files: `apps/web/src/lib/actions/kyb.ts`, `apps/web/src/lib/data/kyb.ts`, business pages and eligibility helpers, `packages/database/prisma/schema.prisma` plus an additive migration, new underwriting/provider modules, `packages/soroban/contracts/business_passport/src/lib.rs`, `packages/soroban/contracts/loan_escrow/src/lib.rs`, SDK/indexer code, and focused tests/CI.
